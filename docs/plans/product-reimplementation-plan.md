# ERD Maker 전체 제품 재구현 계획서

- 작성일: 2026-10-15
- 프로젝트 구조: [디렉터리 설계와 현재 파일 위치](../architecture/directory-structure.md). 문서와 소스 경로는 정리된 현재 경로를 사용한다.
- 상태: **사용자 승인 후 구현 중.** 본문의 입력 조사·초안 상태·미수행 문구는 계획 작성 당시의 기록이다. 승인된 전체 범위는 유지하며 최신 구현·실행 결과는 [현재 상태](../status.md)에서 별도로 관리한다.
- 목표: eXERD 수준의 독립 데이터 모델링 제품. 브라우저와 Electron에서 macOS·Linux·Windows 공통 지원. `.exerd` 가져오기·편집·저장·원본 eXERD 재열기를 포함한 양방향 호환.
- 사용 조건: 새 앱에 계정, 로그인, 라이선스 키, 활성화 서버, 사용 기한을 요구하지 않는다. 로컬 모델 편집과 파일 처리는 오프라인으로 제공한다.
- 우선순위: **P0 데이터 보존·원본 재열기 → P1 전체 모델링·DB 설계 업무 → P2 확장·배포 품질.** P2도 최종 제품 범위에 포함한다.
- 권고: 화면 확장 전에 `.exerd` XML·바이너리 저장 엔진의 타당성을 검증한다. 이 관문을 통과하지 못한 상태를 전체 제품 구현 가능성이 입증된 것으로 보고하지 않는다.

**1. 목표와 완료의 정의**

사용자가 제공한 파일을 새 앱에서 열고, 실제 설계 업무를 수행하고, 저장한 `.exerd`를 원본 eXERD에서 정상적으로 열고 다시 편집할 수 있어야 한다. 소수 테이블의 시연 앱, 읽기 전용 뷰어, SQL 변환기 완성은 중간 단계다.

“거의 완벽”을 평균 점수로 표현하지 않는다. 데이터 손실·의도하지 않은 변경·원본 재열기 실패는 허용하지 않는다. 기능 차이는 항목별로 공개하고, 미구현 항목을 남긴 중간 버전을 최종 완료로 처리하지 않는다. 글꼴·OS 기본 대화상자 등 환경 차이는 모델 의미와 업무 수행 결과에 영향이 없는지 별도로 판정한다.

**3. 파일 호환성에서 먼저 해결할 문제**

파일은 전용 헤더와 버전·XML 구간 길이, 압축 XML, 압축 바이너리 모델을 담고 있다. 바이너리 서명은 공개 EMF(Eclipse Modeling Framework, 객체 모델과 저장 규격) 서명과 일치한다. 그러나 eXERD에는 자체 입력·출력 스트림이 있어 공개 EMF의 기본 코덱과 동일하다고 단정할 수 없다. [공개 EMF 구현](https://raw.githubusercontent.com/eclipse-emf/org.eclipse.emf/master/plugins/org.eclipse.emf.ecore/src/org/eclipse/emf/ecore/resource/impl/BinaryResourceImpl.java)

3.3.56의 `ErdResourceImpl`을 `javap`으로 정적 조사한 결과:

- `skipHeader`는 헤더의 `zippedXmlContentLength`만큼 XML 구간을 건너뛴다.
- `doLoad`는 그다음 ZIP 엔트리를 자체 `EObjectInputStream.loadResource`로 읽는다.
- `doSave`는 XML 구간을 쓰고, 자체 `EObjectOutputStream.saveResource`로 `binary-content`를 쓴다.
- 따라서 **XML만 바꾸고 이전 바이너리를 유지하는 저장 방식은 R03을 충족하는 설계로 채택할 수 없다.**
- 이는 제공된 3.3.56 클래스의 정적 근거다. 사용자 파일을 저장한 3.3.52의 실행 경로·오류 복구 동작까지 확인한 것은 아니다.

세부 근거는 입력 조사 기록의 `serializationInspection`, 로컬 정적 추적은 `.analysis/planning/ErdResourceImpl.javap.txt`에 있다. 원본 클래스 코드를 제품 소스에 복사하지 않았다.

**파일 엔진 관문:** XML과 바이너리를 같은 편집 상태로 생성하고, 원본 eXERD가 그 변경을 읽는 것을 먼저 증명한다. `.erdx`·JSON·SQL로의 대체 저장은 별도 기능이며 `.exerd` 왕복 호환의 완료 증거로 사용하지 않는다.

**4. 기능 범위와 우선순위**

기준 제품은 제공된 eXERD 3.3.56이다. 사용자 파일의 3.3.52와 제공된 2.5.17은 별도 버전 축으로 관리한다. erwin은 기능·업무 흐름의 보완 참고다. 모든 erwin 에디션 전체를 동일하게 구현한다는 의미로 확대하지 않는다.

eXERD 공식 안내는 논리·물리 모델링, 용어·도메인, 자동 배치, 모델 검사, DB 정방향·역방향 처리, 내보내기, ERwin 가져오기를 제품 기능으로 제시한다. [공식 기능 안내](https://exerd.com/down.do)

뷰·시퀀스·사용자 정의 자료형·트리거·파티션·스토리지 등은 DB별 객체 조사표에 포함한다. 제공된 파일에 인스턴스가 없는 객체도 도움말·메타모델·원본 조작으로 존재 여부를 확인하고, 확인된 기준 제품 기능을 명세에 추가한다. 이 표를 전체 세부 명세가 확정된 것으로 간주하지 않는다.

기능별 상태는 **존재 근거 확보 / 명세 확정 / 읽기 / 보존 / 표시 / 편집 / 저장 / 원본 검증 / 완료**로 구분한다. 단순 보존만 되는 기능을 편집 가능 기능으로 집계하지 않는다. 신규·미확인 기능을 발견하면 목록과 공수를 갱신하고 최종 범위에서 임의로 제외하지 않는다.

SAM 전용 저장소·다중 사용자 협업은 제공된 일반판과 구분한다. 새 앱의 로그인 없는 로컬 업무는 필수다. 협업 기능의 제품 포함 여부는 기준 제품 기능 조사에서 별도 결정하며, 사용자 계정을 일반 편집의 선행 조건으로 만들지 않는다.

| eXERD 버전 | 3.3.52 실파일 → 제공된 3.3.56에서 재열기 | 3.3.52·3.3.56 원본과 교차 저장, 2.5.17의 해당 형식 회귀 | 해당 실행 환경 미확보 시 미검증 |
| 형식 버전 | `3.0.0.20190111-1604`와 동봉 샘플 | 제공된 버전의 마이그레이션 분기 및 새로 작성한 파일 | 버전 문자열만 바꾼 저장을 하위 호환으로 인정하지 않음 |
| DBMS | 사용자 파일의 PostgreSQL | Oracle·SQL Server·DB2·MySQL·PostgreSQL·Tibero·MariaDB·CUBRID | 실제 엔진 미검증 항목은 지원 완료로 표시하지 않음 |
| erwin | 공식 문서의 비교·모델 업무 흐름 | eXERD가 지원하는 ERwin 가져오기 범위 조사, 보완 UX | 이진 `.erwin`과 XML·DDL 교환을 혼동하지 않음 |

DB 버전별 자료형·예약어·인용·대소문자·기본값·계산/생성 컬럼·식 인덱스·필터·파티션 등의 지원 행렬을 작성한다. 8개 DB를 한 SQL 생성기로 묶고 예외를 숨기는 방식을 피한다. SQLite 추가 지원은 선택 확장이며, 위 8개 DB의 검증을 대체하지 않는다.

원본 3.3.52 실행 파일은 현재 입력에 없다. 3.3.56에서 열리는 것과 3.3.52에서 열리는 것은 별도 시험이다. 버전별 정상 사용 가능한 원본 환경을 확보한 뒤 교차 저장 결과를 기록한다. 새 앱의 무계정 사용과 원본 제품의 이용 조건은 별개다.

**6. 권장 제품 구조**

```text
브라우저 UI ─────────┐
                    ├─ 공통 명령·모델 엔진 ── 검사·비교·용어·DB 방언
Electron UI ────────┘          │
                              ├─ .exerd 컨테이너 + XML + 바이너리 코덱
                              ├─ 독립 작업 파일 + 변경 기록·복구
                              └─ 다이어그램 모델 ── 렌더링·배치 작업자

Electron DB 연결 프로세스 / 선택적 로컬 연결 도구
              └─ 읽기 전용 메타데이터 수집·드라이버별 변환
```

- **의미 모델:** 테이블·컬럼·키·관계·도메인·제약·DB 고유 객체를 ID로 참조한다. 복합키·인덱스는 정렬된 컬럼 목록과 개별 속성을 가진 객체다.
- **표시 모델:** 업무영역과 다이어그램, 다이어그램별 테이블 배치, 관계선 경로·메모·표시 설정을 분리한다. 좌표를 테이블 자체에 하나만 저장하지 않는다.
- **원본 보존 계층:** 원본 컨테이너·XML/바이너리 구조, 미해석 필드·외부 참조·버전 정보를 유지한다. ID와 공유 참조를 이름으로 대체하지 않는다.
- **편집 명령:** 컬럼 이동·테이블 삭제 등 명령마다 참조 영향 검사, 변경 기록, Undo/Redo, 직렬화 영향을 함께 정의한다.
- **형식 어댑터:** `.exerd`, 독립 작업 파일, SQL, ERwin 교환 형식을 분리한다. 독립 파일의 신규 기능이 `.exerd`에서 표현 불가능할 때 저장 전 차이를 설명한다.
- **DB 방언 어댑터:** DB별 타입·키·제약·인덱스·DDL·메타데이터 규칙을 분리하고 원래 DB 정체성을 보존한다. 미지원 DB를 PostgreSQL로 바꿔 저장하지 않는다.
- **비동기 작업:** 파싱·코덱·모델 검사·배치·비교는 작업자 스레드로 분리하고 진행률·취소·메모리 한도를 둔다. [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)
- **로컬 저장:** 브라우저는 IndexedDB 기반 작업·복구 기록과 파일 내보내기를 병행한다. 설정 외 모델 본체를 localStorage에 저장하지 않는다. Electron은 임시 파일·동기화·교체·백업으로 원자적 저장을 구현한다. [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB)

브라우저의 직접 파일 저장 API를 필수 조건으로 삼지 않는다. 지원 환경은 직접 저장을 제공하고, 다른 환경은 파일 선택·다운로드로 같은 모델을 처리한다. 브라우저 저장 용량·권한 거부·사생활 보호 모드·여러 탭 충돌도 복구 시험에 포함한다. [File System API](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API)

Electron의 DB 드라이버와 파일 권한은 UI에서 격리한다. 최소 범위의 프로세스 간 인터페이스를 정의하고 `contextIsolation`, sandbox, 입력 검증을 적용한다. [Electron 보안 지침](https://www.electronjs.org/docs/latest/tutorial/security)

**7. 기술 선택 비교**

| 선택지 | 장점 | 비용·제약 | 계획 판단 |
|---|---|---|---|
| 공통 TypeScript 엔진 + 브라우저/Electron | 동일 기능·파일 시험을 재사용, 설치 없이 접근 | 바이너리 코덱·대형 렌더링을 직접 검증해야 함 | **권장 기본 구조** |
| JVM/EMF 중심 데스크톱 | 기존 EMF 동작과 비교하기 쉬움 | 브라우저에서 동일 엔진 실행이 어려움 | 분석·교차 검증 보조 후보 |
| 서버 중심 웹 앱 | 중앙 DB 연결·배포 관리가 쉬움 | 오프라인·무계정 로컬 사용에 서버 의존성이 생김 | 선택적 연결 기능으로만 검토 |
| 원본 플러그인을 새 UI에서 실행 | 단기 기능 재사용 가능성 | 독립 엔진·브라우저 공통 실행·배포 의존성 문제 | 기본 제품 구조로 채택하지 않음 |

- **바이너리 코덱:** TypeScript 독립 구현을 먼저 검증한다. 처리량·메모리 수치가 부족하면 Rust/WASM을 비교한다. JVM 보조 도구는 분석 환경에 사용할 수 있으나 최종 브라우저 파일 편집의 필수 의존성으로 두지 않는다.
- **렌더러:** React Flow와 Canvas/WebGL 기반 대안을 사용자 실파일·확대 모델로 비교한다. DOM 컬럼 전체 렌더링의 비용과 접근성·텍스트 편집·벡터 출력의 비용을 함께 측정한다. [React Flow 성능 지침](https://reactflow.dev/learn/advanced-use/performance)
- **자동 배치:** Dagre·ELK 등의 후보를 복합 관계·큰 업무영역·수동 경로 보존으로 평가한다. 라이브러리 채택만으로 eXERD 수준의 결과라고 판정하지 않는다.
- **초안의 기존 의존성:** 설치됐다는 이유로 채택을 확정하지 않는다. 라이브러리·코덱·렌더러는 위 관문 결과로 결정한다.

**8. REA와 원본 분석 절차**

REA는 조사 흐름과 근거 관리에 사용한다. Eclipse/Java 플러그인은 JAR·메타모델·바이트코드·실행 관찰이 핵심이다. REA의 실제 연결 도구와 해당 버전 지원 범위를 확인하고 필요한 Java 분석 도구를 병행한다. REA 설치 또는 실행 사실을 코드 이해의 증거로 대신하지 않는다. [REA 공식 스킬](https://github.com/morluto/rea/blob/main/.agents/skills/reverse-engineer-anything/SKILL.md)

1. 원본 파일·JAR·샘플의 버전과 해시를 고정하고 분석 사본을 만든다.
2. 기능 질문을 파일 저장, 도메인 전파, 관계 동기화, DDL, 배치 등으로 분리한다.
3. 도움말·`plugin.xml`·`.ecore`에서 객체·기능·등록 경로를 대조한다.
4. 저장·읽기 경로부터 메서드 호출·자료형·직렬화 옵션을 조사하고 관측 명세를 작성한다.
5. 원본에서 작은 모델을 만들어 한 번에 한 속성만 변경하고 저장 전후 차이를 비교한다.
6. 관측 명세를 바탕으로 독립 구현하고, 원본과 다른 도구로 결과를 재검증한다.
7. 결론마다 입력 버전·정적 근거·실행 근거·미확인을 연결한다. 동일한 의존성을 가진 두 자체 테스트를 독립 근거로 세지 않는다.

이번 조사 방식은 표준 라이브러리 기반 컨테이너/XML 조사와 `javap` 정적 분석이다. 현재 세션에서 원본 eXERD를 실행하거나 REA 도구로 원본 동작을 관찰한 것은 아니다. 추후 도구 설치·설정은 구현 착수 범위에서 별도로 수행한다.

**9. `.exerd` 양방향 호환 구현 전략**

| 순서 | 검증 과제 | 산출물 | 다음 단계 진입 조건 |
|---|---|---|---|
| C1 | 헤더·버전·엔트리·크기·CRC·XML/바이너리 표기 조사 | 컨테이너·코덱 명세와 경계값 표 | 사용자 실파일·동봉 샘플에 대한 일관된 해석 |
| C2 | 바이너리 객체·참조·기본값·타입·순서 해독 | 양쪽 표현의 객체별 비교 결과 | 불일치·미해석 의미 목록과 원인 확인 |
| C3 | 무편집 재직렬화 | 독립 writer와 원본 재열기 기록 | 객체·속성·참조·배치의 의미 차이 0건 |
| C4 | 단일 속성 편집 | 편집 전후 기대 차이 명세·원본 확인 | XML/바이너리·원본 UI에 동일 변경 반영 |
| C5 | 참조를 바꾸는 구조 편집 | 복합키·도메인·이동·복제·삭제 사례 | 의도된 변화 외 차이·고아 참조 0건 |
| C6 | 원본과 반복 교차 저장 | 10회 이상 왕복 결과와 버전별 비교 | 누적 손실·자동 보정·변경 소실 0건 |
| C7 | 신규 모델·DB별 확장·구버전 | 형식·버전·DB별 호환 행렬 | 해당 행렬의 수용 시험 전부 통과 |

무편집 저장에서는 헤더·압축 시간 등 허용 가능한 비의미 차이를 사전에 목록화한다. 문자열·객체 순서·타입 표현을 임의로 정규화하지 않는다. 원본이 저장 시 자동 갱신하는 버전·뷰 상태 등은 실제 동작을 확인한 뒤 허용 차이에 추가한다.

원본 바이트를 그대로 반환하는 테스트는 복사 경로만 증명한다. **재직렬화와 편집 후 원본 재열기 테스트를 별도로 통과해야 한다.** 미지의 필드를 원시 데이터로 보관하는 것만으로 충분하지 않으며, 참조 대상이 편집될 때 미지 필드도 일관되게 처리되는지 확인한다. 이를 판단하지 못하면 해당 편집의 `.exerd` 저장을 제한하고 원인을 설명한다.

**10. 수용 시험 설계**

모든 결과는 원본 입력 해시, 앱 빌드 식별자, eXERD 버전, OS, 변경 명령, 저장 파일 해시, 비교 보고서, 화면·로그를 연결한다. 원본 `REF/`에 저장하지 않고 검증 사본과 결과를 별도 디렉터리에 둔다.

| 시험 ID | 업무 시나리오 | 통과 조건 |
|---|---|---|
| A01 | 사용자 실파일을 새 앱에서 처음 열기 | 전체 객체·속성·38개 다이어그램·53개 메모 조회, 오류·누락 목록 없음 |
| A02 | 수정 없이 `.exerd` 재직렬화 후 원본 열기 | 오류/누락/예기치 않은 보정 없음, 의미 차이 0건 |
| A03 | 원본 이름·논리명·주석·기본값 편집 | 변경 대상과 참조·유도값의 기대 차이만 발생 |
| A04 | 컬럼 추가·이동·삭제와 Undo/Redo | 참조·순서·인덱스와 양쪽 표현의 일관성 |
| A05 | 복합 PK·대체키·FK 생성 및 재매핑 | 컬럼 순서·부모/자식 대응·NULL·참조 동작 일치 |
| A06 | 도메인·용어 변경과 예외 컬럼 | 참조·상속·타입·이름 전파 결과 일치 |
| A07 | CHECK·고유 제약·DB 물리 속성 편집 | 표현식·옵션이 원본과 실제 DB 메타데이터에 유지 |
| A08 | 같은 테이블을 두 다이어그램에서 각각 이동 | 모델 객체는 공유, 좌표·표시·선 경로는 독립 |
| A09 | 메모·테마·선·인쇄 옵션 편집·출력 | 배치·스타일·한글·페이지 설정 재열기 유지 |
| A10 | 원본 수정·저장 → 새 앱 재열기, 10회 교대 | 반복 횟수에 따른 정보 감소·값 변형 없음 |
| A11 | 새 앱에서 새 모델 생성 → 원본 열기 | 복사한 원본 없이 객체·DB·다이어그램 생성 가능 |
| A12 | DDL 생성 → 임시 DB 적용 → 역공학 | 실제 DB 구조가 모델 의도와 일치, 차이 이유 명시 |
| A13 | 모델·DB 비교, rename·선택 병합·변경 SQL | 의존 순서·미선택 객체 유지·실제 DB readback |
| A14 | 잘림·CRC 불일치·미지 버전·과대 압축·DTD 입력 | 원본/기존 작업 보존, 명확한 실패, 무한 대기 없음 |
| A15 | 저장 실패·중단·디스크 부족·탭 충돌·재시작 | 마지막 정상 파일 보존, 확인된 복구 지점 제공 |
| A16 | OS·브라우저를 바꿔 파일 열기·수정·저장 | 플랫폼 이동에 의한 의미·한글·숫자 손상 없음 |
| A17 | 빈 계정 설정·네트워크 차단 상태에서 새 앱 실행 | 로그인·활성화·구독 확인 없이 편집·내보내기 |
| A18 | 스크립트 일괄 변경·취소·실패 | 허용 범위 내 변경, 트랜잭션·복구·Undo 정상 |
| A19 | ERwin 교환 파일·정의서·이미지·인쇄 | 지원 형식·객체별 결과 대조, 누락·잘림 0건 |

객체 수가 같아도 속성·관계 방향·복합키 순서가 다를 수 있다. 개수 비교는 첫 검사이며 최종 검사는 UUID별 속성·참조·배치 비교와 원본 실제 재열기로 한다. 파싱·자체 테스트·원본 재열기·DB 실행·사용자 업무 수용은 서로 독립된 증거로 보고한다.

**11. 성능·복구 목표**

아래 수치는 **개발 수용 목표 제안**이며 측정 결과가 아니다. G0에서 CPU·RAM·OS·해상도·브라우저 버전과 측정 방법을 고정한다. 16GB RAM급 개발 환경을 초기 비교 기준으로 삼되 최저 지원 사양은 실측 후 결정한다.

| 항목 | 초기 수용 목표 | 측정 조건 |
|---|---|---|
| 사용자 실파일 가져오기·참조 검사 | 5초 이내 | 609개 테이블·10,045개 컬럼, 처음 읽기 |
| 다이어그램 전환 | 300ms 이내 | 사전 로드 후, p95(100회 중 느린 5회를 제외한 경계) |
| 선택·속성 반영 | 100ms 이내 | 즉시 피드백 p95, 저장 완료와 분리 |
| 일반 이동·확대 | 30fps 이상 | 현재 다이어그램과 전체 배치 스트레스 시험 |
| 사용자 실파일 `.exerd` 저장 | 5초 이내 | XML/바이너리 생성·검증 포함, 디스크 기록 별도 표기 |
| 새 앱 모델 검색 | 200ms 이내 | 전체 객체 검색 p95 |
| 자동 저장 복구 지점 | 마지막 편집 5초 이내 | 저장 실패와 종료 중단을 포함 |
| 반복 사용 | 1시간·열기/닫기 20회 | 상태 누락·재현성 있는 메모리 누적 원인 해결 |

확대 시험은 원본을 변경하지 않고 ID·참조를 일관되게 재생성한 2배·5배 모델을 만든다. 약 1,218/3,045개 테이블 규모의 열기·검색·다이어그램 전환·저장 수치를 원본과 함께 보고한다. 모든 컬럼을 한 화면에 렌더링하는 방식과 업무영역별 표시를 각각 측정한다. 성능 미달 시 원본 객체를 줄여 통과시키지 않는다.

**12. 플랫폼과 오프라인 동작**

| 제품 형태 | 필수 검증 환경 | 공통 기능 | 환경별 확인 |
|---|---|---|---|
| Electron | macOS Apple Silicon·Intel, Windows x64, Linux x64 | 전체 편집·코덱·복구·파일·DB 연계 | 설치·실행·IME·글꼴·인쇄·서명·업데이트 |
| 브라우저 | macOS의 Chrome/Firefox/Safari, Windows의 Chrome/Edge/Firefox, Linux의 Chrome/Firefox | 모델 편집·코덱·파일·출력 | 파일 권한·다운로드·저장 용량·오프라인 재실행 |
| DB 연결 | Electron 연결 프로세스 또는 선택적 로컬 연결 도구 | 같은 메타데이터 계약·DB 방언 | OS별 드라이버·인증서·인코딩·접속 취소 |

버전 하한은 G0의 환경 목록에서 지정하고 출시 시 실제 버전을 기록한다. Windows ARM·Linux ARM은 별도 확장 행으로 관리한다. 해당 아키텍처 미검증을 macOS·Linux·Windows 전체 지원 완료로 표현하지 않는다.

브라우저는 초기 설치·캐시 후 오프라인 재실행 또는 로컬 정적 서버 배포를 지원한다. `file://`에서 모든 웹 기능이 된다고 가정하지 않는다. DB 연결만 선택적 로컬 도구를 사용할 수 있으며, `.exerd` 편집·저장은 브라우저 단독으로 동작해야 한다.

기본 빌드에 외부 로그인·라이선스 확인·기간 제한·원격 모델 업로드·필수 분석 SDK를 넣지 않는다. 사용자 DB의 기존 인증정보는 DB 접속에만 사용하며 새 앱의 계정 생성과 분리한다. 앱을 오프라인으로 실행하는 시험과 DB에 접속하는 시험을 구분한다.

**15. 기존 구현 초안의 취급**

이전 턴에 생성된 코드는 제품 기반으로 확정하지 않는다. 이번 조사에서 요구 규모와 데이터 구조 차이가 확인됐다.

| 현재 초안 | 확인한 공백 | 착수 후 처리 방침 |
|---|---|---|
| `app/src/core/model.ts` | 테이블당 좌표·업무영역 하나, 제한된 제약·관계·DB 표현 | 전체 모델 계약을 먼저 설계하고 교체 필요성 검토 |
| `app/src/formats/exerd/import.ts` | XML 일부 매핑, 바이너리 무해석, `.exerd` writer 없음 | 조사 보조로 분류, 왕복 코덱 완료 증거로 사용하지 않음 |
| `app/src/formats/sql/ddl.ts`, `app/src/core/validation.ts`, `app/src/core/diff.ts` | 제한된 모델 계약·DB 범위 기반 | 새 명세와 실제 DB 결과에 맞춰 재평가 |
| UI·Electron·CI 초안 | 화면 구성·설정과 실제 플랫폼 동작이 별개 | 렌더러·환경 결정 후 재사용/교체 판단 |

이번 작업에서는 해당 소스·설정·설치 상태를 수정하거나 삭제하지 않는다. 추후 재사용은 명세 적합성 검토를 통과한 부분에 한정한다. 기존 테스트 통과 수를 전체 제품 완성도로 환산하지 않는다.

**16. 다음 착수 시 먼저 제출할 결과**

1. **기능 추적표:** F01~F24를 실제 메뉴·속성·명령·예외 단위로 세분화하고 원본 근거를 연결한다.
2. **코덱 명세:** XML·바이너리 타입/참조·헤더·길이·버전·migration 규칙과 불명확한 부분을 기록한다.
3. **원본 비교 실험표:** 작은 테스트 모델에서 한 속성씩 변경하는 원본 조작과 기대 파일 차이를 정한다.
4. **왕복 검증 보고서:** 사용자 실파일과 작은 모델을 각각 저장·재열기해 데이터·화면·DB 결과를 구분한다.
5. **공수 재산정:** 관측된 바이너리 난도·미확인 기능·환경 확보 상태에 따라 계획을 수정한다.

현재 완료한 것은 입력 조사와 이 계획서다. 제품 코드 구현, `.exerd` 저장, 원본 재열기, DB 실행, 플랫폼별 동작은 이번 작업에서 수행하지 않았다.
